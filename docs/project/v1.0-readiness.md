# v1.0 Stable Specification Readiness

This page records the current repository-controlled readiness of ONDTF for promotion from **v0.9.0 Candidate Specification** to **v1.0.0 Stable Framework Specification**.

The authoritative machine-readable readiness state is [`governance/v1.0-readiness.yaml`](https://github.com/sankarshanmukhopadhyay/open-national-digital-trust-framework/blob/main/governance/v1.0-readiness.yaml). The governing maturity model remains [`governance/maturity.yaml`](https://github.com/sankarshanmukhopadhyay/open-national-digital-trust-framework/blob/main/governance/maturity.yaml).

## Current conclusion

**ONDTF is not yet promotion-ready for v1.0.0.**

Four of the nine repository-controlled gates are currently evidenced as satisfied. Four require explicit stable-release evidence and one is blocked by unresolved repository-governance work.

| Gate | State | v1.0 judgment |
| --- | --- | --- |
| Normative stability | `evidence-required` | Candidate coherence exists; stable promotion still needs an explicit normative freeze and material-change rule. |
| Identifier stability | `satisfied` | Generated identifier validation provides deterministic duplicate and resolution checks. |
| Requirement/conformance traceability | `satisfied` | All 28 candidate requirements are represented in the conformance and requirements machinery. |
| Deterministic validation | `satisfied` | Repository, schema, integration, documentation and publication checks fail closed through CI. |
| Adversarial/negative evidence | `evidence-required` | Negative evidence exists, but stable promotion needs an explicit sufficiency matrix across consequential failure domains. |
| Compatibility/change control | `evidence-required` | The stable v1.x contract needs explicit enforceable change classes and version/evidence consequences. |
| Errata process | `evidence-required` | Evidence invalidation exists; stable maintenance still needs a bounded errata/emergency-correction process. |
| Blocking-issue disposition | `blocked` | [Issue #5](https://github.com/sankarshanmukhopadhyay/open-national-digital-trust-framework/issues/5) remains open and potentially release-relevant. |
| Release integrity | `satisfied` | The v0.9.0 payload has deterministic integrity, manifest and coherence validation suitable as the v1.0 baseline. |

## Residual work to reach stable

The remaining work is bounded and repository-controlled:

1. **Normative freeze and change classification** — record the v1.0 normative baseline, define material normative change, and require reassessment of affected readiness evidence after material changes.
2. **Adversarial coverage sufficiency** — publish a coverage matrix mapping authority, scope, lifecycle, freshness, revocation, recognition, remedy and other consequential failure domains to executable negative vectors or governed assessor procedures.
3. **Compatibility policy** — define backwards-compatible, materially normative and breaking change classes, including versioning, migration and evidence-invalidation effects.
4. **Errata and emergency correction** — define intake, decision authority, scope, supersession, notification and evidence-reassessment rules.
5. **Blocking issue disposition** — complete issue #5 or make an explicit evidence-backed non-blocking judgment for each residual control before this gate can pass.

These are not external implementation dependencies. They are work ONDTF can execute and test itself.

## Promotion rule

`v1.0.0` may be marked promotion-ready only when **all nine** repository-controlled gates are `satisfied`.

The validator `scripts/validate_v1_readiness.py` cross-checks the readiness register against `governance/maturity.yaml`. It fails when a required gate is missing, duplicated, unknown, assigned an invalid state, lacks evidence or residual-work semantics, or when `promotion_ready: true` is asserted while any gate is unsatisfied.

Missing `E2`, `E3` or `E4` evidence remains missing evidence. It constrains claims of independent implementation, cross-implementation interoperability or operational deployment; it neither blocks specification stability nor compensates for an unsatisfied repository-controlled gate.

## Evidence and revocation

A readiness state is not permanent merely because it once passed. A material normative change, invalidated evidence, superseded implementation assumption or discovered defect can require a gate to return to `evidence-required` or `blocked` until reassessed.

The v1.0 release decision therefore remains an explicit human governance decision made against machine-verifiable evidence, rather than an automatic consequence of CI success.
