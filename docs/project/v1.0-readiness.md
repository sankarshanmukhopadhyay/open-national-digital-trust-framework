# v1.0 Stable Specification Readiness

This page records the current repository-controlled readiness of ONDTF for promotion from **v0.9.0 Candidate Specification** to **v1.0.0 Stable Framework Specification**.

The authoritative machine-readable readiness state is [`governance/v1.0-readiness.yaml`](https://github.com/sankarshanmukhopadhyay/open-national-digital-trust-framework/blob/main/governance/v1.0-readiness.yaml). The governing maturity model remains [`governance/maturity.yaml`](https://github.com/sankarshanmukhopadhyay/open-national-digital-trust-framework/blob/main/governance/maturity.yaml).

## Current conclusion

**ONDTF is not yet promotion-ready for v1.0.0.**

Eight of the nine repository-controlled gates are now evidenced as satisfied. The remaining gate is deliberately `evidence-required` until the implementation issues for the four stable controls are closed by merge; the readiness register does not pre-emptively treat open release work as complete.

## Stable-control evidence

The four previously missing repository-controlled controls are now represented by executable artifacts:

- [`governance/v1.0-normative-freeze.yaml`](https://github.com/sankarshanmukhopadhyay/open-national-digital-trust-framework/blob/main/governance/v1.0-normative-freeze.yaml) binds the proposed stable surface and defines material-change reassessment.
- [`governance/v1.x-change-control.yaml`](https://github.com/sankarshanmukhopadhyay/open-national-digital-trust-framework/blob/main/governance/v1.x-change-control.yaml) defines enforceable compatibility semantics for the v1 line.
- [`governance/errata-and-emergency-change.yaml`](https://github.com/sankarshanmukhopadhyay/open-national-digital-trust-framework/blob/main/governance/errata-and-emergency-change.yaml) governs ordinary and emergency correction, supersession and reassessment.
- [`governance/v1.0-adversarial-coverage.yaml`](https://github.com/sankarshanmukhopadhyay/open-national-digital-trust-framework/blob/main/governance/v1.0-adversarial-coverage.yaml) makes negative-evidence sufficiency explicit across thirteen consequential domains.
- `scripts/validate_v1_stable_controls.py` validates those artifacts and executes deliberate falsification fixtures for normative drift, breaking change without migration, authority-free emergency correction, and an orphan adversarial domain.

The institutional-role catalogue and provider-lifecycle metadata were also reconciled from stale draft labels to the v0.9 candidate state before their bytes were admitted to the proposed stable freeze. Their substantive semantics were not changed by that metadata correction.

Issue #11 remains a bounded repository-security evidence task. Missing evidence there stays `evidence-required`; it is not converted to PASS and does not currently invalidate the stable specification contract.

## Promotion rule

`v1.0.0` may be marked promotion-ready only when **all nine** repository-controlled gates are `satisfied`.

The validators `scripts/validate_v1_stable_controls.py` and `scripts/validate_v1_readiness.py` enforce the stable controls and readiness state. A `blocked` readiness gate must declare machine-readable blocking conditions rather than relying on historical prose or a bare issue reference.

Missing `E2`, `E3` or `E4` evidence remains missing evidence. It constrains claims of independent implementation, cross-implementation interoperability or operational deployment; it neither blocks specification stability nor compensates for an unsatisfied repository-controlled gate.

## Evidence and revocation

A readiness state is not permanent merely because it once passed. A material normative change, invalidated evidence, superseded implementation assumption or discovered defect can require a gate to return to `evidence-required` or `blocked` until reassessed.

The v1.0 release decision therefore remains an explicit human governance decision made against machine-verifiable evidence. **Promotion-ready is not released**, and neither state implies E2/E3/E4 evidence.
